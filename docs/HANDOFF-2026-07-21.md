## What the displayed data means today

This distinction is important and is not yet obvious enough in the UI.

### Dune fields

The token cohort comes from the latest completed result of Dune query `4124453`.
It is a rolling recent window, not a calendar-day creation bucket. For each
token, the current code prefers Dune's values for:

- `marketCap` (the query's market-cap estimate at Dune execution time);
- `priceUsd` (the query's VWAP price); and
- `tradeCount`.

The app does not trigger query `4124453`; a successful app sync can download a
result that Dune executed earlier. Health now detects when that execution grows
too old.

### DexScreener fields

At sync time the app selects the Solana pair with the highest reported
liquidity and uses it for:

- token name, image, banner, website, and socials;
- 24-hour volume, liquidity, and 24-hour price change; and
- pair creation time.

These are values captured when the snapshot was written. Historical tabs do not
re-fetch DexScreener and therefore preserve the values captured for that daily
snapshot.

### Date tabs

`Latest 24h` is today's most recently stored rolling Dune window. A tab such as
`24h to Jul 20` is the last stored rolling window for that UTC snapshot date.
It does not mean every displayed token was created on July 20. Each UTC date has
one snapshot that is replaced by later successful syncs on the same date.

## Accuracy audit findings

A bounded sample of eight live tokens was compared with DexScreener immediately
after deployment using the same highest-liquidity-pair rule.

- Pair creation timestamps matched for all 8/8 sampled tokens.
- Volume and liquidity were identical or reasonably close for most tokens; the
  expected differences reflect market movement since the stored sync.
- Displayed market cap and price sometimes differed dramatically from current
  DexScreener values. This is expected from the code: those two fields come from
  the older Dune execution, not from DexScreener. In the sample, several were
  close, while others had moved by roughly 7x, 92x, or more.

Therefore the site is internally consistent with its current source mapping,
but the unlabeled `Market Cap` column must not be interpreted as guaranteed
real-time DexScreener market cap. This is the largest current functionality/UX
accuracy problem.

Live field coverage at audit time (30 tokens):

```text
marketCap, liquidity, volume24h, priceUsd, priceChange24h,
tradeCount, createdAt: 30/30
image, bannerImage: 25/30
graduatedAt, observedPeakMarketCap, observedPeakAt,
measuredVolumeUsd, buyCount, sellCount: 0/30
sourceExecutionEndedAt: 30/30 after the first post-deploy snapshot write
```

`sourceExecutionEndedAt` matched the snapshot's Dune execution timestamp on all
30 live tokens.

The optional peak/buy/sell fields are plumbing only. Query `4124453` does not
return them, so the site does not yet display or possess ATH data.

## Remaining risks and gaps

1. **Mixed-source metrics are under-labeled.** Market cap/price are from Dune;
   volume/liquidity/change are from DexScreener at a later time.
2. **Dex pair identity is not retained or fully validated.** The code chooses
   the highest-liquidity Solana pair but does not store its pair address or
   verify that the requested mint is the base token before using base-token
   metadata.
3. **Dex volume is one pair, not aggregate token volume.** The UI currently
   labels it simply as 24h volume.
4. **No ATH exists yet.** Optional peak fields are empty until a controlled Dune
   query calculates and returns a defensible observed peak.
5. **No description/about field exists.** Images, banner, website, and socials
   are the available profile enrichment.
6. **The production Dune query is externally controlled.** Its logic, cadence,
   and availability remain outside this repository.
7. **One snapshot per UTC date loses intraday states.** A token that runs and
   collapses between snapshots may not be represented at its peak.
8. **The scheduled background endpoint remains public.** This is accepted for
   now because functionality/UX has priority; the dispatcher/authenticated
   worker redesign remains noted in `PLAN.md`.
9. **Fresh mobile visual verification remains incomplete.** The in-app browser
   ignored its viewport override. Mobile fixtures and the stored production
   baseline pass, but the deployed responsive layout should be checked manually.
